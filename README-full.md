# 天象预报模块（kuangchujia.com）

**一句话定位**：把「离线 Python 预计算」与「WordPress 页面渲染」切开的一套模块——天文量全部在本机由 `compute_sky.py` / `build_dataset.py` 算好后经 REST 端点入库，插件短代码只读自建数据表，前端**零实时计算**；对外提供每日天象、天象事件列表、历史天象回推三类内容。

**当前版本 v2.1.0（2026-09-23）**。v2.0.0 是「观测地维度 ＋ 三个子项」版（见 §1.4）；**v2.1.0 把「历史上今日天象」从只做月食扩到三族自算**（见 §1.5）—— 起因是一条**产品判据**：只收月食时 288 条摊到 366 个「月-日」上**只覆盖 133 天（36.3%）**，232 天打开是空的。v1.3.0 是结构化数据归属修正版（见 §1.3）、v1.2.1 是线上首推修复版（见 §1.1）；v1.2.0 是「按《WordPress 站点天象模块落地指令集》指令 01—10 执行」的产物：主代理先校验该指令集（发现其与既有 v1.1.0 交付包冲突、自身有内部矛盾与事实性错误），逐项裁定后再执行，故部分指令为「改道执行」而非照抄。

**v1.2.1 是线上首推修复版** —— v1.2.0 真实装到站上之后，第一次推数据**没写进去**。修掉的是两个**读代码看不出来、推着真数据跑才暴露**的缺陷（F22 列宽溢出、F23 两份正本列类型分岔），外加一条「插件升级后旧列宽没人带上来」的架构缺口。见 §1.1。

**v1.3.0 是结构化数据归属修正版** —— 面板里 `Schema Type` 选了 `Event`，79 条事件详情页却**整页零 JSON-LD**（连 Person / WebSite 都没有）。一路排除后**读 Rank Math 免费版源码定谳**：它的白名单只认 Article 家族 ⇒ 面板这条路根本走不通。同轮还揪出「日期为空的 `Dataset`」坏节点，并为本项目补上了**第一套 PHP 层判据**。见 §1.3。

### 1.1 v1.2.1 增量（线上首推修复版）

v1.2.0 交付并**真实安装到线上**后，首次向 `wp_astro_daily` 推送 1 行数据**失败**。下面几项都不是读代码能读出来的，是**推着真数据跑一遍**才暴露的：

| 类别 | 缺陷 | 证据（线上实测） | 修法 |
|---|---|---|---|
| **数据无法入库**（阻断） | **F22 · 列宽溢出**：`data_version` / `dt_model` 列宽 `VARCHAR(32)`，而 F17 把版本号从 27 字符改成 `de421+dt_espenak_meeus_2006+tt_scale`（**36**），解析降级行再加 `+analytic`（**45**）。列注释里写的就是 36 字符的值，**列宽没跟着改** | REST 回执 `written:0, failed:1`，`errors:["…失败：data_version。提供的值可能太长或包含无效数据。"]`；**A/B/C 边界实验**：36 字符拒、**32 字符进**、34 字符拒 ⇒ 列宽恰为 32 | 两份正本同步放宽到 `VARCHAR(64)`；`build_dataset.py` 的 `COL_MAXLEN` 补 `data_version`（v1.2.0 **根本没登记它**）、`dt_model` 32→64；`_daily_row` 的 `data_version` / `method` 接上 `_clip` |
| **静默吞错**（恶化） | `compute_sky.push_rest()` 只读回执里的 `written`，**丢掉 `failed` 与 `errors[]`** ⇒ 服务端拒写被显示成「写入 0 行」，排查时毫无线索 | 客户端输出 `写入 0 行（累计 0/1）`；手动 POST 同 payload 才拿到完整 `errors` | 逐批打印 `failed` 与 `errors` 前 3 条；`failed>0` 时抛错（调用方本就有 `exit=2` 分支，此前永远走不到） |
| **升级路径缺失**（架构） | `dbDelta` 只在**激活钩子**里跑 ⇒ 插件升级后，已建库的旧列宽**没有任何机制**被带上来 | 站点三表建于 v1.2.0，列宽停在 32 | 新增 `KCJ_ASTRO_SCHEMA` 表结构版本常量（与插件版本**解耦**）＋ `init` 守卫：option 不符即跑 dbDelta 增量升级 ⇒ **重传插件后无需重新激活，首次访问自动 ALTER** |
| **两份正本类型分岔** | **F23**：`event_type` 在 `install_tables.sql` 里是 `ENUM(...)`、在 dbDelta 正本里是 `VARCHAR(32)`，而校验器**只比列名不比类型**，一直没暴露 | 新加的列类型对拍**首跑即报红**：`SQL=ENUM('SOLAR_ECLIPSE',…) / PHP=VARCHAR(32)` | 统一为 `VARCHAR(32)`（以 dbDelta 为准 —— 它才是真正建表的那份，线上表本来就是 VARCHAR），原 ENUM 取值清单移入 `COMMENT`，信息不丢 |
| **校验器失职**（根因） | `check_sql()` 只对拍**列名集合** ⇒「列太窄装不下真值」与「两处类型不同」**都查不出来**；`check_zip()` 只验「文件在不在」⇒ **源件改了、zip 没重打**也查不出。150 项全绿，仍然上线即错 | —— | 新增**列类型/列宽逐列对拍** ＋ **列宽 ≥ 实测最长值**（从真数据收集，不从声明自证）＋ `COL_MAXLEN` 与 SQL 列宽一致性 ＋ **zip 内容与磁盘逐字节一致**；负控制 9→**15** 项 |
| 工程卫生 | 插件包此前是**手工打的** ⇒ 文件集靠记忆、字节不可复现 | —— | 新增 `make_zip.py`：文件集由磁盘现状决定、时间戳固定 ⇒ 连打两次字节完全相同（`--selftest` 已验） |

**第二批（同日，v1.2.1 尚未上线 ⇒ 并进同一个包，不另升版本号）** —— 修完 F22 后回头审升级路径本身，又挖出三个**同族**缺陷（都属「系统以为自己升级了，其实没有」）：

| 类别 | 缺陷 | 证据 | 修法 |
|---|---|---|---|
| **同一 option 两处语义不同**（潜伏，真 bug） | **F24**：`activation.php` 把**插件版本** `KCJ_ASTRO_VER` 写进 option `kcj_astro_schema_version`，而 `create()` 写的是 `KCJ_ASTRO_SCHEMA`。两者语义不同 ⇒ 只要取值撞车，`init` 守卫就误判「已升级」，**永久跳过 ALTER** | 静态对拍：同一 option 出现两种写入值（`['KCJ_ASTRO_SCHEMA','KCJ_ASTRO_VER']`） | 该写入点删除，表结构版本**只由 `create()` 一处落账**；新增判据「同一 option 的所有写入点语义必须唯一」＋两向负控制 ⑱⑲ |
| **升级也会静默失败**（同族） | **F25**：`create()` 跑完 `dbDelta` 就**无条件落账** ⇒ ALTER 一旦失败也被记成「已升级」，守卫从此不再重试，列宽**永远补不上**。**F26**：`/health` 不暴露表结构状态 ⇒ 只能靠「推一行数据看报不报错」试错判断升级成没成 | —— | `create()` 改为**逐列实测列宽**：达标才落账；不达标记 `kcj_astro_schema_error` 且**不写版本**，留给下一次请求重试（自我修复）。`/health` 新增 `schema` 段：option 值 / 期望值 / **实测列宽** / 缺口清单 |
| **失败只报个数、不报原因**（同族） | `rest-import.php` 有两处 `$failed++; continue;` **不记 `$errors[]`** ⇒ 客户端看得到「失败 N 行」、看不到为什么 | 新判据扫出 2 处 | 补上原因文案；新增判据「每个 `$failed++` 都带得出原因」＋负控制 ⑳㉑ |

★ 这一批还顺带**验证了 dbDelta 会改列宽**：查 WordPress 核心 `wp-admin/includes/upgrade.php` 的 `dbDelta()` —— 它取 `DESCRIBE` 的 `Type` 做**全串**比较，`varchar(32) !== varchar(64)` 且 varchar **不命中** text/blob「向短退让」与整数显示宽度两个例外 ⇒ **必定发出 `ALTER TABLE … CHANGE COLUMN`**。所以 F22 的升级路径成立，不必手工跑 SQL。

**F22 的深层教训**（已写入技能 `checker-self-reference-pitfalls`）：**判据写在了被测变换的下游**。第一版补的判据是「产出值不超 `COL_MAXLEN` 声明列宽」——可 `_clip` 已经先裁过一遍，裁剪之后自然不超宽 ⇒ **该判据恒真**。负控制当场把它抓了出来。正确的不变量在**上游**：`_clip` **从不该需要触发**；一旦触发就是列宽装不下真值，属于静默数据失真，必须报出来而不是悄悄截掉。

#### （二）v2.1.0：历史栏目从「只做月食」扩到**三族自算**

**为什么要扩（实测数字，不是推测）**：只收月食时，288 条摊到 366 个「月-日」上，

逐族量过年率与覆盖后才决定扩族：

| 族 | 年率（12 年样本） | 覆盖月-日（12 年样本） | 依据 |
|---|---|---|---|
| 月食 | 2.29 | 133 | 本模块自有求根引擎，已与 NASA GSFC 目录逐条对拍 |
| **流星雨** | **15.00**（＝群数） | **38** | 极大时刻 ＝ 太阳 **J2000 黄经**达该群约定 λ☉ 之时；λ☉ **照录 IMO／RASC**，与年份无关 ⇒ 非自造 |

> ★ **全量实测结果（2026-09-23 跑完，126 年 1900—2025）**：
> 共 **4,672 条**（月食 **288** ／ 流星雨 **1,890** ／ 行星天象 **2,494**）、用时 **1,831 s（≈30.5 分钟）**、

**v2.3.1 的一件事（修 F61 线上致命错误）**：v2.3.0 新加的多行快路径把语句拼装写在
`$flush` **闭包**里，闭包内用了 `$wpdb` —— 而 **PHP 闭包不继承任何外层作用域**，
函数顶部那句 `global $wpdb;` 到不了闭包里面 ⇒ 闭包内 `$wpdb` 为 `null` ⇒ 首次
`$wpdb->prepare()` 即 `Call to a member function prepare() on null`，**导入端点整个 500**
（用户站点健康页的截图即此）。修法：闭包体内**再声明一次** `global $wpdb;`
（不用 `use ($wpdb)`：capture-by-value 抓的是**定义那一刻**的值，初始化顺序一变就会静默
捕获 `null` —— 同一故障的第二次）。**比缺陷本身更值钱的一条**：这条路径
**从未被任何判据执行过**（桩 WPDB 连 `query()` 都没有）——「判据没覆盖」≠「判据通过」。

1. **「天象」标题列被「说明」挤到只剩 110px** ⇒ 21 字标题折成 3 行；

> ① 拿 `<td>` 的 `offsetHeight ÷ line-height` 当「几行」—— `<td>` 会被**同行最高格**撑高，

> 格子里有 `<a>` 时同一行会被**重复计一次**（2 行被数成 4）。正解：按 **distinct `top`** 去重计数。

★ **`side` 默认 `future` 的理由**：历史月食与未来事件同表（`wp_astro_events`），
不加过滤会把「1919 年的日食」混进「未来预告」列表里 —— 这类错误在页面上**看起来很正常**，
故设为默认值而非可选项。

★ **`[astro_history_today]` 的 `types` 默认含 `solar_eclipse`（而日食**一条都没收录**）是刻意的**：
默认族里带上它，页面才会如实打出一句「**该族在历史段一条都没收录 ⇒ 属未录入，不能据此说这一天没有**」。
若因「反正没数据」把它删掉，**这句如实说明也跟着消失** —— 等于把「没查」重新藏回「没有」。
