# 可行性评审报告 · 天象预报模块 v1.0.0 → v1.1.0

> 结论先行：**v1.0.0 不能上线，不是「细节待打磨」，而是「第一句就崩」。**
> `compute_daily()` 的第一次调用会抛 `TypeError`；历史回推功能整体不可用；
> 入库路径在 WordPress.com 上物理封闭；样例数据是手写占位数。
> 本轮共查出 **16 项**影响可行性的缺陷（F1—F16），已全部修复并逐条复验。
>
> 复验结果（**v1.1.0 时点**）：`--selftest` **27/27 通过**；`verify_package.py` **67/67 通过**（含 4 项负控制）。
> ⚠ **本节数字只描述 v1.1.0**。当前口径（**2026-09-23 事件模块轮**）：`compute_sky.py --selftest` **31 项** ／ `event_almanac.py --selftest` **227 项** ＋ `--verify` 对拍 **57 项** ／ `verify_package.py` **213 项**（含 **30** 项负控制）／ `build_dataset.py --selftest` **51 项**；v1.2.0 时点分别为 31 / — / 150 / 14。见 `README.md` 与 `docs/verification-report.md`。

## 一、判定方法（为什么这次结论可信）

上一轮（v1.0.0）的通病是**只做了静态审读，没有真正跑过**。本轮换方法：

| 手段 | 作用 |
|---|---|
| 逐条实测 skyfield API（`inspect.signature` + 真调用） | 抓出 4 处 API 误用（F2/F3/F4/F3b），这些**静态看不出来** |
| 装载本机已带的 `de421.bsp`（`skyfield_data` 包）跑通全链路 | 让「能不能跑」从推测变成事实 |
| 与权威实现对拍（Meeus 教材算例 + skyfield 相位根求解） | 让精度声明有依据，而不是自说自话 |
| 负控制（故意注入缺陷，确认校验器报红） | 防「校验器恒真」这一最危险的假绿 |

## 二、缺陷清单与修法

### F1 星历只能联网下载 —— 断网即废
- **病症**：`load('de421.bsp')` 只走联网下载路径。实测本机沙箱 `ssd.jpl.nasa.gov` 返回 **502**，脚本必失败。
- **更关键**：本机 `skyfield_data` 包**已经带了一份 `de421.bsp`**（`site-packages/skyfield_data/data/de421.bsp`），v1.0.0 完全没用上。
- **修法**：五级发现 —— ① `--ephemeris` 显式路径 → ② 环境变量 `KCJ_EPHEMERIS` → ③ 工作目录候选（`./ data/ ephemeris/ python/`）→ ④ `skyfield_data` 内置 → ⑤ 才联网兜底（失败给中文可操作提示）。
- **复验**：离线环境下 `--selftest` 全绿，`--window` 正常打印覆盖区间。

### F2 `epoch='j2000'` 直接抛异常
- **病症**：`apparent.ecliptic_latlon(epoch='j2000')` → `ValueError: the epoch= must be a Time object, a floating point TT, or the string "date"`。
- **修法**：改 `epoch='date'`（当日黄道）。坐标系口径同时明确写进输出字段 `xiu.frame`。

### F3 升落函数签名全错 —— 这是「第一句就崩」的元凶
- **病症**：实测真实签名是 `risings_and_settings(ephemeris, target, topos, horizon_degrees, radius_degrees)`；
  v1.0.0 写成 `risings_and_settings(ts, eph[body], observer, which='rise')` ——
  `ts` 被当成 ephemeris、`which` 参数根本不存在，**必抛 TypeError**。
- **连带**：`topos` 实参必须是裸 `Topos`，不能传 `eph['earth'] + Topos(...)`（内部会再 `+ topos`，导致 `ValueError: you can only add two vectors if...`）。
- **修法**：改签名 + 传裸 `Topos`；并在注释里写明 `state` 语义（1 = 升起 / 0 = 落下），附实测样例。

### F4 晨昏函数签名与语义双错
- **病症**：`dark_twilight_day` 真实签名是 `(ephemeris, topos)` —— 不收 `ts`、不收 `degree`；
  且其返回是 0—4 的**五态**（0=夜 … 4=昼），不是「三条晨昏界」。v1.0.0 的 `_twilight(eph, observer, ts, …, -6)` 参数全错。
- **修法**：改用 `risings_and_settings(eph, eph['sun'], topos, horizon_degrees=-6/-12/-18)`，
  `state=1` → 晨光始（begin），`state=0` → 昏影终（end）。实测 2026-09-22 揭阳：民用 05:40 / 18:33，与 `dark_twilight_day` 的跃迁时刻逐秒吻合。

### F5 星历覆盖区间写错，且「改用 de440s」是错药方
- **病症**：① 文档称历史回推「公元前 2000—公元 3000」；② v1.0.0 注释说「超范围改用 de440s.bsp」。
- **实测**：`de421.bsp` 覆盖 **JD 2414864.5—2471184.5 = 1899-07-28 至 2053-10-08**（不是文件里写的「1900—2050」）；
  `de440s.bsp` 覆盖 **1849—2150**，**同样到不了公元前**。要覆盖公元前 2000 必须用 **DE431 / DE422 / DE441**（体积 GB 级）。
- **修法**：① 建 `EPHEMERIS_PROFILES` 区间表（8 档），按文件名识别 + 运行时守卫；② 覆盖外**降级到 Meeus 解析式**（见下），而不是崩溃或假装能算；③ 注释与文档同步纠正。
- **复验**：`compute_daily(1000,1,1)` 不再崩溃，输出 `method='analytic_meeus'`；`allow_analytic=False` 时明确抛 `OutOfRange` 并给出三种出路。

### F6 距星表未作岁差 —— 宿度系统性偏移
- **病症**：v1.0.0 把 28 距星的 **J2000** 黄经当固定值用。实测 2026 年即偏 **0.38°**；1900 年、公元前更甚。
- **修法**：精算路径改用 skyfield 对 28 距星做 `.apparent()`（与日月五星同一条坐标变换链），按 `(年,月)` 缓存并以该月 15 日为取样点（可复现、与调用顺序无关）。
- **副作用**：距星表与天体从此**同一坐标系**，宿度自洽。
- **局限（已在代码注明）**：距星自行未计（跨 2700 年约 0.04°）；解析降级路径仍用近似式（与精算差约 0.006°，已在注释中如实标注「不作精算口径声明」）。

### F7 逐日重复加载星历 —— 白等十几小时
- **病症**：`compute_daily` 每次调用都 `load()` 星历 + `load.timescale()`。
- **修法**：模块级缓存 `_EPH_CACHE` / `_TS_CACHE`；另加 `--jobs N` 多进程。
- **实测收益**：稳态 **0.253 s/日**（首日含加载 0.89 s）。

### F8 一个合规错误 + 两个正确性错误
- **① `value_xiu_of_day` 已删除** —— 原实现把「太阳所在宿」当「值日星宿」，**两回事**：
  值日星宿是二十八宿**独立 28 日轮值**，与太阳位置无关；且该体系用于择日吉凶，**触本模块「禁吉凶谶纬」红线**。已从脚本、模板、样例、Schema 全链移除。
- **② 行星星等**：原 `_approx_mag` 只用距离做 `5log` 硬凑，误差 1—2 等，据此给出的「肉眼可见 / 需双筒」分级站不住。改 Meeus ch.41 相位角公式（5 颗行星各自的 V(1,0) 多项式 + `cos i` 内/外行星分流）。土星未计环贡献，已在输出标 `mag_note`。
- **③ 朔判据漏回绕**：原 `phase < 5 or abs(phase-180) < 5` 漏掉接近 360° 的朔。改为取到 0°/180° 的最小角距。

### F9 入库路径在 WordPress.com 上物理封闭
- **病症**：`--db` 走 pymysql **直连 MySQL**。但 kuangchujia.com 由 WordPress.com 托管，**不开放外部数据库连接** —— 这条路走不通。
- **修法**：插件新增 `includes/rest-import.php`，暴露三个端点：
  | 端点 | 方法 | 用途 |
  |---|---|---|
  | `/wp-json/kcj-astro/v1/import` | POST | 分批导入（≤500 行/请求），字段白名单，`jd`/`slug` 唯一键 upsert |
  | `/wp-json/kcj-astro/v1/flush-cache` | POST | 清 transient |
  | `/wp-json/kcj-astro/v1/health` | GET | 连通性与三表行数自检 |
  鉴权：HTTP Basic + **应用程序密码**，权限要求 `edit_posts`。Python 侧新增 `--wp-rest`。
- **连带修掉一个不可能**：v1.0.0 让「构建流水线刷新后调用 `do_action('kcj_astro_refresh_cache')`」——
  外部 Python 进程**根本触发不了** WordPress action。现改为**服务端在导入成功后自动清缓存**。

### F10 「正午」名不副实
- **病症**：`ts.utc(y,m,d,12,0,0)` 自称正午，实为北京时间 **20:00**。
- **修法**：`12 − tz_hours`（＝北京时间 12:00）。

### F11 表结构缺溯源列与复合索引
- **修法**：`wp_astro_daily` 加 `method`；`wp_astro_events` 加 `method`、`ephemeris`；
  加复合索引 `(event_type, publish_status, jd_core)` 覆盖 Tab 列表的 `WHERE + ORDER BY`。
- **同步纪律**：`install_tables.sql`（交付件 A）与 `activation.php`（dbDelta）**列集必须一致**，已由校验器逐列对拍。

### F12 历史页「虚假溯源」
- **病症**：详情模板无条件写「回推结果以现代星历（DE421）反演」——而覆盖区间外的事件实际走的是解析式。
  这是**把没做的事说成做了**，比算错更严重。
- **修法**：模板按 `method` 分支：解析路径如实写明「**未使用**行星历表，改以 Meeus ch.25/47/49 截断级数近似」。

### F13 公元前纪年差一年（口径陷阱）
- **病症**：天文纪年以 **0 = 公元前 1 年**。传 `-720` 会被理解成「公元前 721 年」。
- **修法**：新增 `parse_era_year()`，接受 `'720BC'` / `'720BCE'` / `'前720'` / `-719`；
  输出新增 `era_year_display` 与 `year_convention`；CLI 帮助文本同步。
- **复验**：样例 `720BC` → `era_year=-719`、显示「公元前 720 年」。

### F14 样例数据是手写占位数（最该脸红的一项）
| 字段 | v1.0.0（手写） | 实算真值 | 差 |
|---|---|---|---|
| `jd`（2026-09-22） | 2461300.0 | **2461305.667** | 5.7 天 |
| 月相 | 「残月」305.1° | **「盈凸月」126.26°** | **错约 180°** |
| 金星视星等 | −4.2 | **−4.56** | 0.36 等 |
| 历史 `jd`（-720） | 146901.0 | **1458495.76**（最近朔） | 1053 天 |

- **修法**：新增 `--emit-samples DIR`，三份样例**全部由真实计算生成**；并保留 `--selftest` 作持续护栏。

### F15 ΔT 区间方向标反
- **病症**：`time_bj_lower`（名）实为最晚时刻，`time_bj_upper` 实为最早时刻。
  原理：`UT = TT − ΔT`，真实 ΔT 比模型**大** → UT **更早**。若照原标签上页面，会把最早时刻说成最晚时刻。
- **修法**：改名为 `time_bj_earliest` / `time_bj_latest`，并按上式校正方向。
- **复验**：样例 `720BC-02-22` 06:28 < 08:28 < 10:28（最早 < 标称 < 最晚）。

### F16 预计算面不可行
- **病症**：`milestones.md` 写「182 万日记录，按年分片」。实测 **0.253 s/日** → 182 万日 = **46 万秒 ≈ 128 小时 ≈ 5.3 天**（单核）。对个人站不可行。
- **修法**：改分档（见 `docs/milestones.md`）——
  日粒度只承诺 **1900-01-01 至 2050-12-31（≈5.5 万天）**：单核约 **3.9 小时**、4 进程约 **1 小时**，可行；
  覆盖外**只做事件级**（精选历史/未来天象各数十至数百条），不做日粒度。
- **附带发现**：10 个城市档若全量展开则为 55 万天（约 39 小时）⇒ **日粒度只做默认揭阳**，其他城市按需。

## 五、一句话总评

v1.0.0 的问题**不是「写得不够全」，而是「写得像但跑不了」**——四类 skyfield 调用全错、星历只能联网、入库路径在托管环境物理封闭、样例数据是编的。
v1.1.0 把「像」换成了「能跑」：**每条精度声明都有对拍依据，每条不可能都给了可行的替代路，每个降级都如实标注方法**。

## F17—F21（v1.2.0 落地指令集执行时新发现）

本节记录的是「按《WordPress 站点天象模块落地指令集》（指令 01—10）执行」时新查出的 5 项缺陷（F17—F21）。
与 F1—F16 不同，这一批的共同特征是：**v1.1.0 的自检全绿也照样能通过**——它们要么只在历史回推路径上暴露，
要么只在真实 WordPress 请求生命周期里暴露，要么属「参数收下但不用」的静默误导。

### F17（功能级，最重要）UT 儒略日被当 TT（JDE）喂给 Meeus 级数，漏 ΔT 改正

**病症**
- 解析降级路径与历史回推路径在调用 Meeus 级数前，**未把 UT 儒略日换算为 TT（JDE）**，直接把 UT 当 TT 传入。
- 后果是**时间尺度错位**：古代 ΔT 极大（公元前 720 年约 5.75 小时），时间错位即坐标错位。
- 该缺陷的性质是「**现代年份测不出来**」：2026 年 ΔT 仅约 63 秒，折算成角度可忽略；只有**历史回推**才暴露——
  而历史回推正是本模块的招牌功能。

**证据**（实测，修正前 vs 修正后的偏差量）

| 年份 | 黄经偏差 | 黄纬偏差 |
|---|---|---|
| 公元前 2000 年 | **5.92°** | 0.551° |
| 公元前 720 年 | **3.41°** | 0.336° |
| 公元 1000 年 | 0.20° | 0.018° |
| 公元 2026 年 | 0.01° | 0.001° |

> 读法：公元前 2000 年时黄经偏 5.92° —— 这已远超「日食几何」的判定容差，会让历史日食的「满足/不满足」判反。

**修法**
1. 新增 `jd_ut_to_jde()` / `jde_to_jd_ut()` 两个显式换算函数；两处路径改用 TT。
2. 输出新增 `jd_ut` 字段，并加**自述字段** `jd_scale: "TT (JDE)"`，让口径随数据走、可被外部核对。
3. `CONFIG.DATA_VERSION` 由 `de421+dt_espenak_meeus_2006` 升为 **`de421+dt_espenak_meeus_2006+tt_scale`**。
4. `sql/install_tables.sql` 的 jd 列注释统一为「**TT 尺度**」。
5. 迁移动作：若曾用 v1.1.0 导入过 **1900 年以前或 2053 年以后**的数据，需**重导**这些日期
   （`uk_date_str` 唯一键保证是更新而非新增，不会产生重复行）。

**复验**
- **修正后的判据（实算）**：公元前 720 年 2 月 22 日算出**日月黄经差 2.101°、月球黄纬 0.269°** ⇒ 满足日食几何，
  与《春秋》隐公三年「春王二月己巳，日有食之」相符；最近朔时刻 **720BC-02-22 08:28**，不确定度区间 **06:28 ~ 10:28**。
- 自检新增两项断言并全绿：`F17 历史回推已做 UT→TT 折算`（实测 `jd_tt − jd_ut = 0.239454 天`，ΔT ≈ 20689 s，
  与 `0.239454` 应相等）、`F17 尺度字段自述（jd_scale）`。校验器另有 `历史样例已做 UT→TT 折算（F17）` 与
  `未来样例 jd_core 为 TT 尺度（F17）` 两项对拍。

### F18 同一史事两份日期互相矛盾，且引了现代注本

**病症**
- 同一件史事（鲁隐公三年日食）在 `compute_sky.py` 的 `selftest` 与 `emit_samples` 里**各写一份日期**：
  `selftest` 用 `(-720, 7, 1)`，`emit_samples` 用 `720BC` → `-719, 2, 22`，**相差一年半**。
- 两处都是手写常量，等于**同一事实有两个真值源**，任何一处改动都会让另一处变成假数据。
- 附带问题：`source_ref` 引的是现代注本（杨伯峻《春秋左传注》），属近现代作品引用。

**证据**
- 两处常量并排比对即现：`(-720, 7, 1)` 与 `(-719, 2, 22)`；差值约 1.5 年，远超任何时间不确定度区间。

**修法**
1. 收敛为模块常量 **`SAMPLE_HISTORICAL`** 作**单一真值源**，`selftest` 与 `emit_samples` 同源取值。
2. 新增断言「**纪年解析与示例常量一致**」，防再次漂移。

## F22—F23（v1.2.1 · **真实上线后首次推数据**才暴露）

这一批与 F17—F21 的区别更极端：**v1.2.0 的三条自检（31/150/14）全绿，插件也确实装上了、三表也建成了**，

### F22（阻断级）`data_version` / `dt_model` 列宽装不下自己写入的值

**病症**
- 列宽 `VARCHAR(32)`；而 F17 把版本号从 `de421+dt_espenak_meeus_2006`（27）改成
  `de421+dt_espenak_meeus_2006+tt_scale`（**36**），解析降级行还会再拼 `+analytic`（**45**）。
- **列注释里写的就是 36 字符的那个值** —— 也就是说改动时想到了这个值，**唯独没回头看列宽**。
- 后果：`wp_astro_daily` 的 `data_version`、`wp_astro_events` 的 `dt_model` 两列，
  任何一次真实写入都会被 MySQL 拒（严格模式下**不是截断，是整行失败**）。

**证据（线上实测，非推断）**
- REST 回执：`received:1, written:0, failed:1`，
  `errors:["WordPress 数据库错误：处理以下字段的值失败：data_version。提供的值可能太长或包含无效数据。"]`
- **A/B/C 边界对照实验**（只变长度，其余全同）：36 → 拒；**32 → 进**；34 → 拒 ⇒ 列宽恰为 32。
  （详见 `docs/verification-report.md` §9.1.1）

**修法**
1. `class-astro-db.php` 与 `sql/install_tables.sql` **两份正本同步**放宽到 `VARCHAR(64)`；
2. `build_dataset.py` 的 `COL_MAXLEN` 补 `data_version`（v1.2.0 **根本没登记它**）、`dt_model` 32→64；
   `_daily_row()` 的 `data_version` / `method` 接上 `_clip`；
3. **升级路径**：新增 `KCJ_ASTRO_SCHEMA`（表结构版本，与插件版本解耦）＋ `init` 守卫，
   option 不符即跑 `dbDelta` ⇒ 已建库站点**无需重新激活**，首访自动 ALTER。

**同批修掉的两个「帮凶」**
- **静默吞错**：`compute_sky.push_rest()` 只读 `written`，丢掉 `failed` 与 `errors[]`，
  把「服务端拒写」显示成「写入 0 行」。已改为逐批打印 `errors` 前 3 条，且 `failed>0` 时抛错
  （调用方本就有 `exit=2` 分支，此前永远走不到）。
- **手工打包**：`wp-astro-forecast.zip` 此前手工打，文件集靠记忆、字节不可复现。
  新增 `make_zip.py`（文件集由磁盘现状决定 ＋ 固定时间戳 ⇒ 连打两次字节相同）。

### F23（一致性）`event_type` 在两份「必须逐列一致」的正本里类型不同

**病症**：`install_tables.sql` 写 `ENUM('solar_eclipse',…)`，dbDelta 正本写 `VARCHAR(32)`。
**为什么一直没暴露**：v1.2.0 的 `check_sql()` **只对拍列名集合，不比类型**。
**修法**：统一为 `VARCHAR(32)`（以 dbDelta 为准 —— 它才是真正建表的那份，线上表本来就是 VARCHAR），
原 ENUM 取值清单移入 `COMMENT`，信息不丢；并新增**列类型/列宽逐列对拍**判据防复发。

### ★ 元教训：判据的「失职」比缺陷本身更值得记

F22 与 F23 是**同一个盲区**的两面 —— 校验器只在一个维度上做对拍（**列名**），
于是「列太窄装不下真值」和「两处类型不同」**都查不出来**。150 项全绿，上线照错。
这与本项目既有的自指族缺陷同源：**判据覆盖的维度，就是你能看见的世界**。

其次，修 F22 时我第一版补的判据是「产出值不超 `COL_MAXLEN` 声明列宽」—— **它是恒真的**：
`_clip` 已经先裁过一遍，裁剪之后自然不超宽。**负控制当场把它抓了出来。**
正确的不变量在**上游**：`_clip` **从不该需要触发**；一旦触发即列宽装不下真值，属静默数据失真，必须报出来。
（两向负控制已锁死：⑩ 列宽过窄必被抓、⑪ 列宽充足不误报、⑫ 类型分岔必被抓、⑬ 类型一致不误报、⑭ zip 与磁盘字节差异必被抓、⑮ 一致时不误报。）

**同一处盲区还有第三个面**：`check_zip()` 只验「**文件在不在**」。⇒ **源件改了、zip 忘了重打**这种最常见的交付事故**完全查不出来** —— 用户上传的是旧代码，而收工闸门全绿。
已补：**zip 内每个条目的字节 == 磁盘同名文件的字节**（逐条比对）。
这与 F22/F23 是同一个句式：**比了「有／无」和「叫什么」，没比「是什么」。**

## F24—F26（v1.2.1 第二批 · 修完 F22 后回头审「升级路径」本身）

F22 的修法是「在 `init` 上加一个 dbDelta 增量升级守卫」。守卫写完当天，我把它当审查对象又过了一遍
—— 挖出三个**同族**缺陷，都属同一个句式：**系统以为自己升级了，其实没有。**

### F24（真 bug，潜伏）同一个 option 被两处以不同语义写入

**病症**：`includes/activation.php` 里写的是
`update_option('kcj_astro_schema_version', KCJ_ASTRO_VER)` ——
把**插件版本**写进了**表结构版本**的 option；而 `class-astro-db.php` 的 `create()` 写的是 `KCJ_ASTRO_SCHEMA`。

**后果**：`init` 守卫的判断是 `get_option(...) !== KCJ_ASTRO_SCHEMA`。
只要插件版本号与表结构版本号在某次取值上**撞车**，守卫就会误判「已升级」⇒ **永久跳过 ALTER**
—— 这正是 F22 的失败模式本身：**表结构升不上来，而系统认为升过了。**

**修法**：该写入点删除 —— 表结构版本**只由 `create()` 一处落账**（单一语义源）。

**防复发判据**：`schema_option_writers()` 收集**全插件**对 `kcj_astro_schema_version` 的所有
`update_option` 写入值，**必须恰好只有一个**（`['KCJ_ASTRO_SCHEMA']`）。
它不比「有没有那行字」，比的是「所有写入点是不是同一个值」。
两向负控制 ⑱（两处不同语义必被检出）／⑲（语义一致不误报）。

### F25（同族）`create()` 无条件落账 ⇒ ALTER 失败也被记成「已升级」

**病症**：`create()` 跑完 `dbDelta` 就直接落账。

**后果**：ALTER 一旦因任何原因没生效（权限、超时、平台限制），option 已被写上 ⇒
**守卫从此永不再试** ⇒ 列宽永远补不上，而 `/health` 看起来一切正常。

**修法**：`dbDelta` 之后**逐列实测**列宽（`SHOW COLUMNS` 读 `Type`，解析 `varchar(N)` 的 N）：
- 达标 ⇒ 才落账（此后每次请求只多一次 `get_option`，成本可忽略）；
- 不达标 ⇒ 缺口写进 option `kcj_astro_schema_error`，**不写版本** ⇒ 下一次请求自动重试（自我修复）。

**防复发判据**：`create_guard_findings()` 检查 create() 里「先实测、后落账、未达标即提前返回」三件事是否齐，
并**断言实测的位置在落账之前** —— 判据若坐在被测流程的下游就恒真，这正是 F22 的元教训。

**旁证**：查 WordPress 核心 `wp-admin/includes/upgrade.php` 的 `dbDelta()` 确认它会改列宽 ——
它取 `DESCRIBE` 的 `Type` 做**全串**比较（`varchar(32) !== varchar(64)`），
且 varchar **不命中** text/blob「向短退让」、整数显示宽度两个例外 ⇒ **必定发出 `ALTER TABLE … CHANGE COLUMN`**。
所以本次升级路径成立，不必手工跑 SQL。

### F26（可用性）`/health` 不暴露表结构状态 ⇒ 只能靠试错判断升级成没成

**病症**：想知道 ALTER 有没有生效，此前只有一条路 —— **推一行数据进去看报不报错**。

**修法**：`/health` 新增 `schema` 段：`option` / `expected` / `ok` /
`widths`（**实测列宽**）/ `shortfalls` / `error`。重传插件后**一眼可判**，不必再拿真数据当探针。

### 附带：失败只报个数、不报原因（同族）

`includes/rest-import.php` 有两处 `$failed++; continue;` **不记 `$errors[]`** ⇒
客户端只看到「失败 N 行」，看不到为什么。已补原因文案；
判据 `failed_without_reason()` 扫全文件 —— 每个 `$failed++` 之后必须出现 `$errors[]`。两向负控制 ⑳㉑。

### ★ 两处自纠（都发生在动手之后、上线之前）

1. **`width_shortfalls()` 第一版把「达标」也写成了缺口**：先无条件赋值、再靠 `strpos($v,' < 需要 ')` 过滤
   —— 而每个值都被拼上了「< 需要」，过滤条件对**全部**项成立 ⇒ 永远报缺口
   ⇒ 守卫**每次请求都跑一遍 dbDelta**。修法：改成「达标不加入」的**独立分支**。
   为此把该逻辑的**等价实现**（`width_shortfalls_py()`）放进校验器，配两向负控制 ⑯⑰ ——
   「达标必须不在清单里」当场可验，不必等上线才发现。
2. **判据被自己的说明文字绊倒（自指陷阱）**：每一条修复都要在注释里写出「改前是什么样」，
   而判据是文本扫描 ⇒ **扫到注释就假报**。修法：`check_schema()` 一律先 `strip_php_comments_only()` 再扫。
   负控制 ㉒（注释里的旧写法不误报）／㉓（同一行写在**代码**里则必被检出）锁死这一对。

### F39（非阻断 · 无法规避）并入 Rank Math `@graph` 的标量会被 WordPress 核心串化

| 字段 | 本地源码 | 线上实收 |
|---|---|---|

**证据链**

1. Rank Math 渲染 JSON-LD 前跑一次 `wp_kses_post_deep( $json )` —— `includes/modules/schema/class-jsonld.php` **L164**。
2. WordPress 核心里 `wp_kses_post_deep( $data )` ＝ `map_deep( $data, 'wp_kses_post' )` —— `wp-includes/kses.php` **L2516—2518**。

* ⚠ **只对「真值」无害**：若将来要发 `false`，会被写成**空字符串 `""`**（既非布尔也非合法布尔串）。**本插件的布尔一律只发 `true`** —— 若哪天要为假值发声明，**必须整个键省略，而不是发 `false`**。
* **本轮不动代码**：v1.3.0 包已上线、指纹已对外（`63,657 B`／SHA1 `615314a7…`），
  上面这条约束只是**注释级**、不改行为 ⇒ 暂记在本文档，**随下次改包时再补进 `rankmath.php` 的注释**，
  免得为一句注释换掉已生效的包。

### F40（非缺陷 · 已定谳）「已有文章级 schema 就让位」不会造成空洞

F37 的修法之一是：**该文章已有自身 `rank_math_schema_*` 元数据时，本插件不再输出 `Event`**（避免同页两个 `Event`）。
当时留了个疑点没验：**让位之后，Rank Math 到底会不会真把那份 schema 渲出来？** 若不会，那篇文章就会静默丢掉全部内容级结构化数据。

**定谳（源码级，两路互证）**

1. **会渲，且不看白名单**：`add_schema()` 挂在 `rank_math/json_ld` **优先级 10**（`includes/modules/schema/class-frontend.php` **L47**），实例化点在 `includes/modules/schema/class-jsonld.php::setup()` **L58 `new Frontend();`**（`class-schema.php` L59 先调 `( new JsonLD() )->setup()`）；函数体是 `array_merge( $data, DB::get_schemas( $post->ID ) )`（同文件 **L218—222**），**没有任何类型白名单** —— 与 `get_default_schema_type()`（只认面板默认值，L70 白名单）是两条独立路径。**注意：`Frontend` 不在 `setup()` 的 `$this->action(...)` 清单里，是靠 L58 的 `new` 挂上的 —— 只读 setup 的挂载清单会误判成「没人调用」。**
2. **站点级实体也保得住**：`can_add_global_entities()` 在走到白名单那一步之前，有 `if ( ! empty( $schemas ) ) return true;`（同文件 **L383—386**）⇒ 有文章级 schema 时直接放行。

⇒ **两个分支都安全**：有文章级 schema ⇒ 让位（Rank Math 出它那份 ＋ 站点级实体照出）；没有 ⇒ 我们出 `Event`（并在优先级 5 撑住 `! empty( $data )`，站点级实体照出）。**不存在「两边都不出声」的组合。**

### F42（数值正确性 · 静默丢数据）升落窗口把 **UTC 日** 当成北京日用

**症状**：真跑 38 城时，**乌鲁木齐的 `sunrise_bj` 为 `None`** —— 不报错、不警告，

_rise_set() 里：ts.utc(y, m, d, 0, 0, 0) ~ ts.utc(y, m, d, 23, 59, 59)

1. **口径错**：窗口起点已是北京时 08:00，配出来的「日出」其实是**次日**的日出

### F43（数值正确性 · 系统性偏差）地平线口径少了**太阳视半径**，全体早/晚 1.4 分钟

### F44（一致性 · 两处实现差一天）「未来十二个月」的两种算法在**闰日附近**分岔

**症状**：同一句「未来十二个月」，PHP 与 Python 两份实现给出的**止日不同**。

**取证**（`_diag/probe_period_split.py`，真跑四种写法对比）：

| 基准日 | PHP 旧（`+12 months`） | PHP 新（日历月） | PY 旧（`+365 天`） | PY 新（日历月） |
|---|---|---|---|---|
| 2026-09-23 | 2027-09-23 | 2027-09-23 | 2027-09-23 | 2027-09-23 |
| **2027-03-01** | 2028-03-01 | 2028-03-01 | **2028-02-29** ← | 2028-03-01 |
| **2027-12-31** | 2028-12-31 | 2028-12-31 | **2028-12-30** ← | 2028-12-31 |
| **2028-02-29** | **2029-03-01** ← | 2029-02-28 | 2029-02-28 | 2029-02-28 |

**分岔 3/5** —— 两个错法各错一半，且**只在闰日附近显现**：

* `+365 天`：起算年与止年之间跨过一个闰日 ⇒ **少一天**；
* `strtotime('+12 months')`：目标月没有该日（2/29）时 PHP 会**进位到下月 1 日**。

**修法**：两侧统一为**日历月加法**，并**明确定义**「目标月没有该日时取该月最后一天」。
PHP 用 `date('t', mktime(...))`，Python 用 `calendar.monthrange()`，两处同构。

**判据（两层，缺一不可）**：

1. **静态哨兵**（`verify_package.py` §12 H 组）—— 禁回退到两条错法。
   **必须先剥注释再扫**：警示「不许这么写」的注释里**必然**写着那两串字符，
   不剥注释，哨兵当场被自己的文档绊倒（本轮实测：两条新哨兵一起误报，而代码已改对）。
2. **跨语言动态对拍**（`php_selftest.py`）—— 真跑 PHP，**5 个基准日 × 4 种期间**
   逐一比对。基准日**必须**含「起算年是闰年」与「起算日恰是闰日」两种成因，
   否则等于没测。

**★ 归类教训**：**判据只在一部分取值上有效 ⇒ 等于没有判据**。
「5 个基准日里 3 个能验出分岔」才是这条判据存在的意义；
用固定的 `today` 去测，永远得到「通过」。

### F45（判据自身出错 · 把常识当事实）「最长月全食 = 2018-07」这条断言是错的

**症状**：`history_events.py --from 1900 --to 2025` 算出 **288 条月食**后
**拒绝写盘**，报：

```
[FAIL] 最长全食位置不符 —— 最长全食落在 2000-07-16（106.6 分钟），期望 2018-07
```

**裁定：判据错，自算对。**

**取证（一手源）**：

| 事件 | 权威值 | 自算 | 差 |
|---|---|---|---|
| **2000-07-16** | NASA LEplot：`Total = 01h46m24s` = **106.4 分钟** | 106.6 分钟 | **+0.2 分钟** ✓ |
| 2018-07-27 | `1h42m57s` = **102.95 分钟** | 102.9 分钟 | −0.05 分钟 ✓ |

**根因**：「2018-07-27 是 21 世纪最长月全食」是**媒体口径**，而**没错** ——
**2000 年按天文纪年属 20 世纪**（EarthSky 原话：
「2001 is technically the first year of the 21st century」）。
本模块的窗口是 **1900—2025**，跨了世纪 ⇒ 区间内最长的确实是 2000-07-16。
**错的是我把「世纪归属」当成了「跨区间最长值」。**

**为什么小样本测不出来**：`--selftest` 用 2015—2025，
在那个窗口里 2018-07 确实最长 ⇒ **判据通过**。
换个区间（1900—2025）才现形 ⇒ **典型的「判据与适用面不匹配」**。

**修法**：

1. **删掉「最长是谁」这类定位断言** —— 定位判据**对区间敏感**，
   「最长」换个窗口就换人，不能当硬断言。区间内的极值改为 **INFO 打印**。
2. 把核证时长**写进参考值逐条比对**（容差 ±1.5 分钟）——
   判据只依赖一手源，不再依赖区间。
3. 另加**与区间无关的物理上限**：全食时长 ∈ `(0, 107]` 分钟
   （月全食时长理论上限约 1h47m）。这类判据换任何区间都成立。

**并补两条负控制**（证明新判据非空壳）：
核证时长写错（102.95→90）必报红；全食时长 200 分钟（超上限）必报越界。

**★ 归类教训（两条，通用）**：

1. **定位判据对区间敏感** —— 凡断言「某某是最大/最早/最长」，
   先问「换个区间还成立吗」；不成立就只能作 INFO，不能作硬判据。
2. **常识必须回溯到一手源才算事实** —— 媒体口径的「世纪之最」在本模块的
   126 年窗口里并不成立；而自算值与 NASA 目录只差 0.2 分钟。
   **判据报红时，先查判据自己，再查代码。**

**根因**：`[20, 60]` 这个区间**是我从旧注释里的一个印象值推的**，不是量出来的。
（当时注释里写着「行星事件每年二三十条」，我把下界抬到 20，而真实值是 19.66。）

**修法**：区间改为 **`[14, 30]`**，并把「**数值必须来自实测**」直接写进判据旁的注释：

```python
RATE_BY_TYPE = {"lunar_eclipse": (1.5, 3.5), "meteor": (12.0, 18.0), "planet": (14.0, 30.0)}
# ★ 判据的数值必须来自实测，不能来自注释里的印象（F47）
```

**★ 归类教训**：**判据的数值必须来自实测，不能来自注释里的印象。**
判据写错的下场与 F45 一样 —— **它会把正确的计算结果判成错的**，
而且**报错信息看起来非常权威**（「[FAIL] 年率不符」），足以让人去改代码而不是改判据。

### F48（正确性 · 静默语义混淆）分组键**一刀切**剥「（…）」，把两种**相反**的天象并成一组

**症状**：为了让「日期锚定型天象历年重现」的条目能折成一组
（英仙座极大落在 8/12，126 年有 126 条），分组键取「标题去掉末尾的日期括号」。
首版正则写成 **剥掉末尾任意括号**。

**取证**：标题样本对拍 ——

| 原标题 | 首版分组键 | 后果 |
|---|---|---|
| `土星留（转逆行）（1918-03-19）` | `土星留` | ⚠ 与下一行**同组** |
| `土星留（转顺行）（1918-06-25）` | `土星留` | ⚠ **「转逆行」与「转顺行」两种相反天象被并成一组** |
| `英仙座流星雨极大（1918-08-12）` | `英仙座流星雨极大` | ✓ |
| `土星合日（1918-01-05）` | `土星合日` | ✓ |

**根因**：括号里既有「**语义限定**」（转逆行／转顺行 —— **必须保留**），
又有「**日期锚点**」（`YYYY-MM-DD` —— **才该剥**）。一刀切剥，等于把语义限定也删了。

**修法**：正则**精确到日期形**：

```php
function kcj_astro_history_group_key($title) {
    $t = (string) $title;
    $k = preg_replace('/\s*（\d{4}-\d{2}-\d{2}）\s*$/u', '', $t);   // ★ 只剥「日期形括号」
    return (is_string($k) && $k !== '') ? $k : $t;
}
```

并把「分组键」**从模板里的内联闭包抽成模块级函数**，让判据与负控制能调**同一份代码**
（见 §F49 末）。`php_selftest.py` 用 5 个标题样本真跑断言，其中两个「留」**必须不同组**。

**★ 归类教训**：**「去掉括号」之前，先问括号里装的是哪一类信息。**
同一外形（圆括号）常混装「限定语义」与「可弃元数据」两类内容；
不区分就删，删掉的是语义而不是噪声。这类错**在页面上看不出来** ——
它会安安静静地把两种相反的天象排版成一组。

### F49（边界 · 自己写不出来的日期）日期跳转用**非闰年**做天数基准 ⇒ `02-29` **永远不可达**

**症状**：历史栏目在「这一天没有收录到天象」时给一条「前后几天」跳转条
（`?kcj_md=MM-DD`），让读者能走到邻日。首版用 `mktime(0,0,0,$mon,$day+$off, 2026)` —— 基准年 **2026（非闰年）**。

**取证**：基准日 × 偏移对拍（`php_selftest.py` 的 harness，4 个基准日 × 4 个偏移）——

| 基准 | 偏移 | 首版（基准 2026） | 应为 |
|---|---|---|---|
| `02-28` | `+1` | `03-01` ❌ | **`02-29`** ✓ |
| `02-29` | `-1` | 写不出来（`2026-02-29` 被 `mktime` 归一到 `03-01`） | `02-28` ✓ |
| `03-01` | `-1` | `02-28` ✓ | ✓ |

**根因**：闰日 `02-29` 在非闰年**根本不存在**，于是
「`02-29` 加一天／减一天」的函数**永远不可能被走到**，
而「从 `02-28` 后一天」也**永远到不了** `02-29`。

**修法**：基准年改用**闰年 2028**：

```php
$ts = mktime(0, 0, 0, (int) $mon, (int) $day + (int) $off, 2028);  // ★ 闰年基准
```

**★ 归类教训**：**凡用「日期 ＋ N 天」做跳转，先问基准年是否有 2 月 29 日。**
这类缺陷的特点是 **① 页面上完全看不出来**（其它 365 天都正常）、
**② 用非闰年做基准的「随机抽查」也测不出来**（要专门挑 `02-28`／`02-29`）。
⇒ 判据必须**显式包含闰日样本**，不能只抽常用日期。

**★ 本轮一条通用范式（已入技能 `checker-self-reference-pitfalls` 与 `php-lint-and-wp-stub-selftest`）**：
**把规则从「模板里的闭包」抽成「模块级函数」，让判据与负控制调同一份代码。**
此前负控制里重抄一遍正则，证明的只是「我抄的那份会报红」——
产品里真正跑的那一份，谁也没验过。
本轮 `rule_history_group_key_date_only()` / `rule_history_nav_leap_base()` /
`rule_no_markdown_bold()` 三条规则都按此抽成函数，负控制 ㉞㉟㊱ 直接调它们。

### F50（平台陷阱 · 判据自己也踩了自指陷阱）PHP 模板里写 markdown 粗体

**症状**：模板输出的是 HTML，而模板里有几处写成了 `**加粗**` ——
在页面上会**原样显示成星号**。为它新写了一条判据「模板里不得有 markdown 粗体」，
**首版一跑就误报 3 条**。

**取证**：3 条命中**全部落在 PHP 注释里** —— 注释里**有意**写着 `**加粗**` 做说明
（例如说明「这里不要写 `**x**`」）。**判据把「说明这个坑的文字」当成了这个坑。**

**根因**：这是本项目**「自指陷阱」的第三例** ——
用「文中出现某字符串」当判据，会让**描述该判据的文档／注释**把自己绊倒。
前两例在 `checker-self-reference-pitfalls` 技能里有档。

**修法**：判据**先剥 PHP 注释再扫**（新增 `strip_php_comments_only()`，
与已有的 `strip_php_tags_only()` 分开 —— 两者的适用面不同）。

**★ 归类教训**：**写「不得出现 X」的判据时，先问「谁的正文里会提到 X」。**
注释、文档、错误提示里**天然**会出现被禁的字串（因为要说明它），
不先剥掉这些区域，判据的**第一受害者就是它自己的说明书**。
