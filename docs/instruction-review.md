# 《WordPress 站点天象模块落地指令集》校验报告

- **被校验件**：`WordPress 站点天象模块落地指令集.txt`，10,077 字节，共 7 章 10 条指令（指令 01—10）。
- **校验日期**：2026-09-22。
- **校验方式**：① 与 v1.1.0 现存交付包逐项对拍；② 对指令集的技术主张**回原始来源核实**（schema.org 官方词表、Rank Math 源码与文档、国家标准信息平台），不凭印象判断；③ 用 `verify_package.py` 的「指令覆盖度」一节做可复跑的门禁。
- **结论**：**主体架构采纳**（插件承载 + CPT 管理事件 + 自定义表存日数据 + 主题模板渲染 + Rank Math 做 SEO，这个骨架是对的）。**但指令集有 3 项事实性错误、4 项内部矛盾、6 处与现存包冲突、5 项落地缺口**，逐条处置见下。

> 本报告只写「指令说了什么」与「核实后事实是什么」。具体怎么改、改到哪个文件，见 `docs/execution-report.md`。

## 一、事实性错误（3 项，均已回原始来源核实）

### 错误 1 ｜ 指令 07：`Calendar` 与 `AstronomicalObject` 在 schema.org 中根本不存在

> **指令原文**（第 145 行）：「今日天象页面：启用「Calendar」+「AstronomicalObject」Schema」

**核实过程**：下载 schema.org 官方词表 release 29.0（`schemaorg-current-https.ttl`，1,063,736 字节），全文检索：

| 类型名 | 官方词表中出现次数 | 判定 |
|---|---|---|
| `AstronomicalObject` | **0** | **不存在** |
| `Calendar` | **0** | **不存在** |
| `Planet` | **0** | **不存在** |
| `Star` | **0** | **不存在** |
| `Constellation` | **0** | **不存在** |

（该词表格式为 `schema:X a rdfs:Class` + `rdfs:subClassOf`，**不是** `a schema:Class`，检索时须按实际格式匹配。）

**性质**：这不是「写得好不好」的问题。**给不存在的类型打标记，等于给搜索引擎投喂无效结构化数据**，Google 富结果测试会直接报错，反而拉低可信度——而指令 07 自己的校验标准正是「Schema 标记无错误」，自相矛盾。

**处置**：今日天象页面改用官方**确实存在**的 `WebPage`（⊂ `CreativeWork`）+ `Dataset`（⊂ `CreativeWork`）。日记录本质就是一份「按日发布的天象数据集」，`Dataset` 是准确且不夸大的类型。参考：`Event`（⊂ `Thing`）、`Article`、`ScholarlyArticle`（⊂ `Article`）、`Place`、`GeoCoordinates`、`Observation`、`Schedule` 均**确认存在**。

### 错误 2 ｜ 指令 07：`ScholarlyArticle` 类型存在，但 Rank Math 免费版够不着

> **指令原文**（第 144 行）：「历史天象事件：启用「ScholarlyArticle」Schema」

**核实过程**：① 该类型在官方词表中**确实存在**（`ScholarlyArticle` ⊂ `Article` ⊂ `CreativeWork`）；② 但查 Rank Math 免费版 Schema 类型清单，**没有** `ScholarlyArticle`；`Custom Schema`（可填任意类型）是 **PRO 专属功能**。免费版清单仅含 Article / Book / CollectionPage / Course / Event / FAQ / HowTo / JobPosting / Music / Person / Product / ProfilePage / Recipe / Restaurant / Service / SoftwareApplication / Video / WebPage / WebSite / BlogPosting / Breadcrumb / NewsArticle / LocalBusiness 等。

**性质**：指令把「类型存在」与「工具支持」混为一谈。**结论是「免费版无路」，不是「类型不对」。**

**处置**：该类型**由本插件自行输出** JSON-LD 补位——这也正是插件存在的意义。同时按 Rank Math 的分工原则：**Rank Math 能做的交给 Rank Math，做不了的插件补**，避免同一页出现两份重复的 `@graph`。可照此分工的还有 `Dataset`（同为 PRO 专属）。

### 错误 3 ｜ 指令 09：GB/T 33661—2017 不规定月相精度

> **指令原文**（第 181 行）：「天象数据基于 NASA JPL DE421 星历计算，**节气与月相符合 GB/T 33661—2017 国家标准**」

**核实过程**：全国标准信息公共服务平台核实该标准全信息——

- 标准名：**《农历的编算和颁行》**（Calculation and promulgation of the Chinese calendar）
- 状态：**现行有效**｜发布 **2017-05-12**｜实施 **2017-09-01**
- 起草单位：**中国科学院紫金山天文台**｜归口单位：中国科学院
- 范围：农历的**编排规则、计算模型和精度、表示方法、颁行要求**
- 规范性附录：**附录 A 二十四节气**、**附录 C 六十干支周**

关键点：**该标准规定的是「什么时候交节」这类编排规则，不规定「月相时刻公布到哪一位」。** 原句把「月相」也纳入符合性主张，属**超出标准范围的主张**。

**性质**：这是合规件里的口径问题，风险高于技术问题——对外声明与国标范围不符，属**可被指摘的表述**。

**处置**：收紧为「**农历日期与二十四节气的编排**符合 GB/T 33661—2017《农历的编算和颁行》」。写入 `includes/compliance.php`，并加入 `verify_package.py` 的负向判据（必须含收紧后的措辞）。

## 二、指令集内部矛盾（4 项）

### 矛盾 1 ｜ 指令 01 与指令 06：模板到底要不要「主题更新不丢失」

- **指令 01**（第 11 行）目标写得很明白：「所有天象功能封装为独立插件，**主题更新不丢失**」。
- **指令 06**（第 125 行）却要求：「将模板文件放到 `wp-content/themes/seedlet/` 目录下」。

放主题目录 = 主题一更新就被覆盖 = 直接违背指令 01 自己定的目标。**两条指令不可能同时成立。**

**处置**：采纳指令 01 的原则。模板**放在插件内** `wp-astro-forecast/templates/`，用 `template_include` 过滤器按 WP 模板层级规则**注入**：主题若自带同名模板则主题优先（尊重用户自定义），没有才用插件兜底。这样既拿到了「主题更新不丢失」，也保住了指令 06 想要的「风格与 Seedlet 统一」。

### 矛盾 2 ｜ 指令 04 与指令 05：事件类型到底是 5 类还是 6 类

- **指令 04**（第 81 行）分类法列 **5 类**：日月食类、行星天象、流星雨、传统天象、历史天象。
- **指令 05**（第 99 行）短代码 `type` 参数列 **6 值**：`solar` / `lunar` / `planet` / `meteor` / `traditional` / `historical`。

同样是「类型」，一处把日月食**合并**成一项，一处**拆成**两项。

**处置**：**两层结构同时满足。** 分类法顶层保留 5 类（其中「日月食」为父项），其下挂 `solar_eclipse` / `lunar_eclipse` 两个子项；短代码的 `type` 参数接受全部 6 个值外加 `all`，并建**别名映射表**（`solar` / `lunar` / `eclipse` 等 9 键），使历史写法与未来写法都能命中。单一真值源放在 `includes/cpt.php` 的 `kcj_astro_event_types()`。

### 矛盾 3 ｜ 指令 04 校验标准漏字，语义相反

> **指令原文**（第 85 行）：「校验标准：发布事件后，前端可通过固定链接正常访问，**404 错误**」

按字面读，这句话的意思是「**应当**出现 404 错误」——与前半句直接相反。显然漏了一个「无」字，应为「**无** 404 错误」。

**处置**：按明显笔误处理，校验标准取「**无** 404 错误」。同时指出：**这条校验标准在 v1.1.0 里是真会红的**，见矛盾 4 / 冲突 3。

### 矛盾 4 ｜ 指令 05 短代码 3 有「用法」无「参数」，且与指令 06 职责重叠

- **指令 05**（第 101—103 行）短代码 3 只写了「自动读取当前事件的关联 ID，渲染同类历史/未来天象」与「自动注入天象事件详情页底部」，**没有参数表**，也没说手工调用时怎么用。
- **指令 06**（第 119 行）又把「古今对照」写进详情页模板的排版序列。

那么「关联」到底是短代码负责，还是模板负责？

**处置**：**两者都做，但只有一个实现。** 短代码 `[astro_related_events id="" mode="auto|historical|future" limit="10"]` 提供手工调用入口；详情页模板内部**直接复用同一个渲染函数**（`templates/astro-related-events.php`），不重复造。`id` 留空则取当前文章。

## 三、与 v1.1.0 现存交付包的冲突（6 处）

| # | 项 | 指令集要求 | v1.1.0 现状 | 处置 |
|---|---|---|---|---|
| 1 | 插件目录名 | `kuangchujia-astro` | `wp-astro-forecast` | **保留现状**。已发布过、URL 与文档均已引用，改名只有成本没有收益 |
| 2 | 数据表数量 | 2 张（daily + relations） | 3 张（daily + events + relations） | **保留现状**。指令 04 要 CPT、04/05 要类型筛选与关联，2 张表承载不了 |
| 3 | 详情页 URL 前缀 | `sky-forecast`（第 79 行） | `/sky/forecast/` | **改从指令**。前缀必须是单段，`/sky/forecast/` 会被 WP 解析成「sky 页面下的 forecast」，改为 `/sky-forecast/{slug}/`，旧址加 **301** |
| 4 | 模板位置 | 主题目录 | 插件 `templates/` | **保留现状**（见矛盾 1） |
| 5 | Schema 类型 | `Calendar` / `AstronomicalObject` / `ScholarlyArticle` | 未实现 | **改从核实后的事实**（见错误 1、2） |
| 6 | 声明口径 | 「节气与月相符合 GB/T 33661—2017」 | 未实现 | **收紧**（见错误 3） |

**补充**：冲突 3 的严重性被低估了。v1.1.0 的**真正必崩缺陷**不在前缀，而在 CPT 注册位置——`register_post_type()` 写在 `register_activation_hook` 里。该钩子**只在激活那一次执行**，之后每个请求都不会再跑；而 WP 需要在**每个请求的 `init`** 上完成注册，才能识别 `/sky-forecast/{slug}/` 这类请求。后果是：**激活后详情页与归档页必然 404**，后台「天象事件」菜单也会消失。这条已修（CPT 与分类法移位到 `init` 优先级 5），并作为**硬判据**写进 `verify_package.py`。

## 四、指令未覆盖、但落地必需的缺口（5 项）

指令集给的是**功能清单**，以下 5 项是「照做也上不了线」的东西：

1. **导入通道**。指令 03 写「插件内编写导入函数，通过 `$wpdb` 批量写入」——**在 WordPress.com 托管下不可行**：平台**不开放外部 MySQL 连接**，外部 Python 进程无法直连数据库。必须改为 REST 端点（`POST /wp-json/kcj-astro/v1/import`）+ WordPress 应用程序密码鉴权。
2. **定时任务的可执行性**。指令 08 要「每月 1 号自动更新未来 12 个月天象」——**插件里跑不了 Python**（无 skyfield、无 de421 星历、且 WP.com 不开放 shell）。**WP.com 还默认禁用真实系统 WP-Cron**（只在有页面访问时才触发）。故该项**降级**为：按时检查数据新鲜度 → 后台提示 → 发 `kcj_astro_need_recompute` 钩子，由站点侧或本地按提示重算推送。**不假装它能自动算天象。**
3. **幂等性**。指令 02/03 完全没提重复导入会怎样。实测三个缺陷：① daily 表唯一键只有 `jd`，而 `jd` 是**计算量**，算法或 ΔT 修正后同一日期会算出不同 `jd` ⇒ 重导**插出第二行**；② relations 表**无任何唯一键** ⇒ 重复导入无限追加；③ 用 `$wpdb->last_error === ''` 判断成功——该变量**不随成功查询复位**，会把上一次的旧错误当成这次的结果。**三项均已修**。
4. **落库字段的口径**。指令 06 要求详情页显示「文献原文 + 史料辨析」，但指令 02 的表结构中**没有**承载它们的列。实际需要：`literature` / `discussion` / `source_ref` / `obs_guide` / `obs_site` / `time_uncertainty` / `dt_model` 等。
5. **数据版本与尺度**。指令集未提。日记录必须能回答「这行数是哪个星历、哪套 ΔT、什么时间尺度算的」。已加 `data_version` 列并在 `data_json` 内标注 `jd_scale`。**这一项在下游暴露了一个真缺陷，见 `docs/execution-report.md` 的 F17**（UT 当作 TT 喂进 Meeus 级数，公元前 720 年黄经偏 3.41°）。

## 五、处置结论

1. **采纳**：01、05、10 全部；02、03、04、08、09 采纳主体并作上述修正。
2. **否决**：06 的「模板放主题目录」；07 的两个不存在的 Schema 类型。
3. **纠正**：07 的 `Calendar` / `AstronomicalObject` → `WebPage` / `Dataset`；09 的 GB/T 引用收紧。
4. **补缺**：第一节列的 5 项全部落地（REST 通道 / Cron 降级 / 幂等三修 / 字段补全 / 数据版本）。
5. **门禁**：`verify_package.py` 的 `check_instructions()` 把上述裁定写成**逐条可复跑的判据**（含「代码中不得出现 `AstronomicalObject`」「CPT 必须在 `init` 注册」「声明必须含收紧后措辞」等负向/正向判据）。**改完再跑，全绿才准交付。**
